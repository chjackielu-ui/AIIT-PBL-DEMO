# Codex 一次性开发执行提示词：安信工项目管理平台 MVP 前端原型

## 一、你的角色与最高目标

你是一名资深 Vue 前端工程师、产品原型工程师和 UI 设计系统工程师。请使用高推理能力完成本项目，但将**尽快实现一个完整、可运行、可交互的实验性前端原型**作为最高优先级。

我会同时提供《安信工项目管理平台_MVP前端原型需求书_视觉规范增强版.md》。该文档是业务范围、业务规则、页面清单、权限、数据关系和验收标准的主要依据。本提示词是对它的执行补充，尤其强调开源项目参考、统一视觉、一次性完成三个端、可靠地启动项目和避免无效验证。

请直接进入工程检查与开发，不要先给我长篇计划，也不要在没有必要的情况下反复向我提问。遇到文档没有明确规定的细节，请选择最简单、最符合现有业务逻辑、最容易演示的方案，并在最终报告中简要说明。

## 二、必须遵守的优先级

发生冲突时，按以下优先级处理：

1. 需求书中明确的业务规则、权限约束和隐私规则；
2. 本提示词中的开发执行、视觉统一和交付要求；
3. 当前仓库已经存在且可用的工程结构、依赖和组件；
4. 开源项目中的成熟交互参考；
5. 你自己的实现偏好。

不要因为参考项目的功能更多，就把它们的复杂功能引入本项目。不要擅自增加需求书明确排除的后端、AI、游戏化、排行榜、私聊、复杂 Git 集成或其他功能。

## 三、开发前的必要检查：短、准、够用

开始时只做必要的工程检查：

1. 检查当前工作目录、文件结构、`package.json`、路由、已有组件、样式文件和 README。
2. 判断当前是否已经存在可运行的前端项目。如果存在，优先在现有工程中修改；不要清空重建，不要为了追求理想目录结构而大规模重构。
3. 如果仓库为空或工程确实无法运行，再建立最简单、稳定的 Vue 3 + Vite 前端工程。
4. 确认当前使用的包管理器和 Node.js 运行环境，优先沿用仓库已有配置，不要随意切换 npm、pnpm、yarn。
5. 不修改 `.env`、密钥、系统级配置以及与本项目无关的文件。
6. 不要在检查阶段耗费大量时间做全仓库扫描、重复搜索或多轮设计讨论。完成判断后立即开始开发。

## 四、必须参考的开源项目

在开发对应模块前，先对照以下开源项目的公开页面、README、截图、组件文档或可访问源码，了解它们如何组织真实业务界面。只需要针对相关模块做有目标的参考，不要进行长时间、无边界的源码研究。

   参考项目工作台、项目导航、任务分配、任务状态、周期/里程碑、项目文档和项目进度组织方式。重点学习怎样让项目概览、任务和进度信息清晰、紧凑地呈现。

3. **Nextcloud** — https://github.com/nextcloud/server  
   参考资料管理中的目录/分类、文件列表、文件操作、上传下载、预览入口和访问权限表达。不要把本项目扩展成完整网盘。

### 4.3 参考规则

- 先研究与当前模块直接相关的页面或组件，再实现该模块。
- 不要求逐行阅读整个仓库，也不要把开源项目源码整体复制进本项目。
- 优先参考界面布局、信息层级、交互习惯和组件使用方式；遵守开源项目的许可证，不直接复制与本项目无关的大块源码。
- 参考项目只是设计和交互依据，本项目仍须服从需求书规定的业务规则与统一视觉规范。
- 如果某个仓库暂时无法访问，不要反复尝试或卡住整个开发；直接换用其他可访问的参考，或使用已安装 UI 组件库中的成熟实现，并在最终报告中如实说明。
- 不要仅凭仓库名称声称已经研究。最终报告只列出实际参考过的项目和对应模块。

## 五、视觉设计：全站强制统一

严格遵守需求书第 9 节。所有学生端、教师端、管理员端都必须使用同一套**蓝色、亮色、简洁、紧凑的 2D 管理系统风格**。

### 5.1 必须做到

- 白色为主背景，蓝色作为全站唯一主强调色；三个端不能分别使用蓝、绿、紫三套主题。
- 不使用渐变、玻璃拟态、光影、投影、发光效果、装饰性大色块背景或非必要动画。
- 不使用 emoji 作为图标；统一使用同一套 SVG 图标库，例如 `lucide-vue-next`。
- 字号、字重、行高、圆角、间距、边框颜色、控件高度、图标尺寸、侧边栏宽度都必须集中定义并复用。
- 页面标题只使用真实业务名称，例如“我的项目”“课程任务”“项目审核”；不要添加欢迎标语、宣传口号、空泛描述和重复副标题。
- 侧边栏图标、文字、点击区域、左侧留白和上下间距保持一致；导航整行可点击。
- 页面紧凑但不拥挤；文字不能被按钮挤压、不能与图标重叠，常用操作必须容易点击。
- 表格、表单、弹窗、状态标签、搜索栏、按钮、空状态等使用统一组件和规范。
- 不要用无意义卡片和装饰性图表填充页面；信息应围绕真实业务组织。
- 不要只追求截图好看，必须同时保证实际操作完整。

### 5.2 实施方式

- 先定义全局设计令牌和基础组件，再实现所有业务页面。
- 如果当前工程已经有可用 UI 组件库，优先沿用，不要同时引入多套大型组件库。
- 全局样式集中定义颜色、字号、间距、圆角、边框、控件高度和图标大小，页面不随意写新的样式值。
- 页面开发完成后做一次整体视觉统一，不要每完成一页就反复进行大量局部重构。

## 六、一次性完成三个端，不能只搭空壳

必须在同一轮开发中完成学生端、教师端和管理员端。三个端都要有登录入口、可访问的页面、真实的前端交互和可用于演示的固定数据。

### 6.1 登录入口

- 应用启动后首先进入登录页面，不要默认直接进入某个角色的工作台。
- 登录页提供学生、教师、管理员三种演示身份入口，并提供预置演示账号或一键进入演示的方式。
- 当前版本没有后端，不要伪装成真实身份认证；页面上可以简洁注明“演示环境”。
- 登录后进入对应角色的工作台，侧边栏菜单随角色切换。
- 用户菜单中允许切换演示身份，便于一次演示所有端；切换后权限、菜单和当前路由应正确更新。
- 提供退出登录并返回登录页的操作。
- 刷新页面后可恢复本地演示会话，但不能把它宣传为安全认证。

### 6.2 学生端必须完成

按照需求书实现学生工作台、可参与任务、任务详情、创建项目、我的项目、项目工作区、任务看板、里程碑/阶段、资料库、项目讨论、成果与结项、成员与贡献、动态记录、通知中心、个人项目档案、历史项目补录、个人履历导出、项目分享预览等页面或功能入口。

学生端不能只展示静态项目卡片。至少要能实际演示：查看教师发布的任务 → 选择队友 → 创建项目 → 提交审核 → 查看审核结果 → 在项目内操作任务、资料和讨论 → 提交阶段成果 → 填写结项材料与个人贡献 → 查看最终评分 → 查看个人项目档案 → 导出个人履历。

严格执行学生权限限制：不能删除项目；不能修改审核通过后的项目基本信息；项目申请提交后不能自行修改正式成员名单；不能给其他学生指派正式任务；不能修改教师评分；不能公开学号。

### 6.3 教师端必须完成

实现教师工作台、课程任务列表、新建/编辑任务、任务详情、跨班组队配置、阶段/里程碑设置、项目申请审核、阶段成果审核、关联项目列表、项目工作区、讨论指导、结项审核、贡献比例确认、个人成绩与评语、可选外部专家评分录入、项目归档/移出归档、项目分享管理等页面或功能入口。

至少能实际演示：教师发布课程任务 → 设置组队规则和阶段要求 → 学生创建项目 → 教师通过或退回申请 → 查看项目过程 → 验收阶段成果 → 审核结项材料 → 确认成员贡献并录入个人成绩 → 自动归档 → 教师移出归档后重新开放项目。

教师只可以查看与其授课、任务发布或审核关系有关的项目。教师可以参与相关项目讨论。外部专家没有账号，评分由教师直接录入。

### 6.4 管理员端必须完成

实现管理员工作台、账号列表、课程/班级/教学班基础数据导入、Excel 模板下载、文件选择、数据预览、基础校验、错误行提示、确认导入、导入结果、项目列表、演示数据恢复等页面或功能入口。

Excel 导入必须有实际前端逻辑，不允许只有一个无效的上传按钮。导入后的新增学生、教师、课程或教学班应出现在相应列表和成员选择器中。若因纯前端环境无法完整实现某种复杂 Excel 场景，应实现一个清楚、可操作的基础方案并说明限制，不要因此阻塞整个原型。

## 七、业务流程和数据一致性

以需求书为准，所有主要流程必须闭环。至少保证：

1. 教师发布的课程任务能被符合条件的学生看到。
2. “允许跨班组队”设置会实际影响成员选择器。
3. 项目申请提交后变为待审核，学生端成员名单锁定。
4. 教师通过/退回后，项目状态、学生页面、通知和工作台统计同步更新。
5. 阶段成果提交后进入待验收；教师通过或退回后状态和反馈同步更新。
6. 任务状态变化能反映到任务看板。
7. 项目讨论消息发送后立即出现，刷新页面后仍保留。
8. @成员会创建对应站内通知。
9. 结项表单必须包含最终成果源文件/代码材料的提交入口。
10. 队长填写的贡献比例总和必须为 100%；不符合时阻止提交并给出明确提示。
11. 教师确认个人成绩和评语后，学生端能看到对应结果。
12. 结项审核通过后项目自动归档；归档项目默认只读；只有教师移出归档后才能继续修改。
13. 分享页不显示学号、聊天记录、内部文件、草稿和中间产物。
14. 关闭分享后，公开链接不能继续展示项目内容。
15. 个人履历 PDF 和项目介绍 PDF 是两个独立导出功能，内容不能混为一份。
16. 恢复默认演示数据后，所有演示状态回到可重复的初始状态。

不要把每个页面做成彼此独立的假数据。项目、成员、任务、文件、消息、提交、评价和通知应来自统一的 mock 数据层或 store。

## 八、前端技术与数据要求

- 仅开发前端，不创建后端、不接真实数据库、不请求真实业务 API。
- 优先沿用当前工程技术栈；如果仓库为空，采用 Vue 3 + Vite + TypeScript + Vue Router + Pinia，并选择一套成熟的 Vue UI 组件库。
- 业务数据统一放入 mock repository/store，避免不同页面各自维护互不相关的假数组。
- 首次启动加载固定种子数据，至少包含三个角色、多个课程/教学班、教师任务、不同状态的项目、阶段成果、讨论消息、资料、贡献比例、评分和通知。
- 关键数据不能每次刷新随机变化。
- 轻量业务状态可使用 `localStorage`；文件二进制优先使用 `IndexedDB`，避免把大文件直接存进 `localStorage`。
- 页面刷新后应保留创建的项目、消息、任务状态、通知已读状态、评分和导入数据。
- 提供“恢复默认演示数据”功能。
- 对浏览器不支持的文件格式给出明确说明；上传或导出失败必须反馈错误，不能假装成功。
- 源码/代码片段使用语法高亮；图片和 PDF 提供预览；无法预览的文件提供下载入口。
- PDF 导出可采用可靠的前端 PDF 方案；如环境确实不支持，可使用打印专用页面作为明确的降级方式，不能让按钮无反应。
- 公开分享路由必须独立于内部工作区，按允许公开的字段构建数据，不能直接将内部项目对象全部渲染到公开页。

## 九、Shell、命令执行与出错换方案规则

开发过程中，稳定推进比使用复杂脚本更重要。

1. 优先使用简单、短小、可理解的命令。尽量避免复杂的多层 shell、长串转义、嵌套引号、依赖 Bash 专有语法的命令和一次性生成大量文件的脚本。
2. 根据当前环境选择命令：Windows 环境优先使用兼容的 PowerShell 命令；如果当前终端是 Bash，则使用简单的 Bash 命令。不要把一种 shell 的语法直接复制到另一种 shell。
3. 文件修改优先使用可靠的编辑工具或直接修改目标文件，不要用复杂 `echo`、多层 here-string 或字符串替换命令写入大量含引号、反引号和中文的代码。
4. 如果某条 shell 命令出错，不要连续重复执行同一条命令，也不要围绕 shell 语法反复试错。先判断错误原因，立即切换到更简单的替代方式，例如拆分命令、使用已有包管理器命令、直接编辑文件或使用当前工具支持的文件操作。
5. 命令失败时保留已有文件和进度；不要执行可能清空仓库、删除依赖目录、重置 Git 状态或覆盖用户文件的危险命令。
6. 不要为了升级 PowerShell、Node.js 或系统环境而中断原型开发，除非当前环境确实无法运行项目且有明确证据。
7. 不要随意修改环境变量、`.env`、系统 PATH 或全局工具配置。
8. 如果依赖安装失败，先判断是否为网络、版本或包管理器问题；优先使用当前工程已有依赖或换用简单、兼容的替代方案，不要陷入长时间安装排障。
9. 任何需要较长时间的命令，都应有明确目的。不要运行与当前原型无关的系统扫描、全量格式化或全仓库检查。

## 十、避免过度验证：先开发，最后集中验收

请严格控制验证成本，不要把高推理能力用在无止境的自我检查、反复计划或大规模重构上。

- 先完成整个原型，再做集中验证。开发过程中只进行必要的局部检查，确保能继续推进即可。
- 不要每实现一个小组件就运行多轮测试、重复审查或重写代码。
- 不要建立复杂的自动化测试框架、端到端测试平台或大量测试脚本；本阶段目标是实验性前端原型。
- 不要因为个别非核心视觉细节不完美就重构整个页面。
- 不要重复验证同一个已经明确通过的事项。
- 只在开发完成后进行一次有针对性的集中验收：安装/依赖状态、项目构建、启动、登录、三个端路由、核心业务闭环、数据刷新持久化、主要页面布局。
- 如果构建或启动失败，修复阻断问题后只重跑必要命令；不要无限循环验证。
- 如果非核心功能受到浏览器限制，采用合理降级方案并记录，不要因此阻塞整体交付。
- 不允许以“还需要进一步规划”“还需要更多测试”为由停在半成品状态。

## 十一、推荐开发顺序：一次性完成全部模块

按以下顺序实施，但不要在每个阶段停下来向我等待确认：

1. 检查工程与现有组件，选择参考项目和 UI 组件库。
2. 建立全局视觉令牌、基础布局、登录入口、角色切换、路由和统一导航。
3. 建立统一 mock 数据层、Pinia/store、本地持久化、固定种子数据和恢复默认数据功能。
4. 完成学生端、教师端、管理员端的工作台和所有主要路由入口。
