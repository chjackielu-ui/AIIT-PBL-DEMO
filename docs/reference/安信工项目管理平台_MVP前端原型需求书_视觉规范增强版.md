# 安信工项目管理平台：最小可运行前端原型需求书

> **文档定位：实验性 MVP / Codex 前端开发依据**\
> 本文档用于先快速实现一个可运行、可交互的基础版本，验证产品主流程。它属于当前实验性开发，不自动代表正式项目的最终需求或技术决策。\
> **本版本明确不开发后端**：全部业务使用前端模拟数据和浏览器本地持久化完成；目标是完整演示流程，而不是支持真实多人在线协作。

-   文档版本：MVP 0.1
-   产品名称：安信工项目管理平台
-   目标用户：学生、教师、管理员
-   主要场景：计算机学院小学期实训中的课程项目组队、项目过程管理、阶段成果验收、结项评价和项目成果展示
-   本次交付：可启动的前端 Web 应用及完整演示数据

------------------------------------------------------------------------

## 1. 产品目标与基本原则

### 1.1 产品目标

建设一个以"项目"为中心的轻量项目管理平台。教师发布课程项目任务，学生围绕任务组队并创建项目，团队在项目空间中完成任务、上传资料、讨论交流、提交阶段成果和最终成果；教师完成审核、过程评价和结项评分。系统同时沉淀团队项目介绍与学生个人项目履历。

### 1.2 核心原则

1.  **项目是协作中心**：项目聚合成员、任务、里程碑、资料、讨论、成果和评价。
2.  **个人档案是成长记录中心**：汇总学生参与过的项目、职责、个人贡献和成绩。
3.  **教师任务驱动组队**：首版只支持课程项目，学生不能脱离教师发布的课程任务自行创建正式项目。
4.  **角色权限明确**：学生、教师、管理员使用同一前端应用，但看到的菜单、数据范围和可执行操作不同。
5.  **前端模拟也必须闭环**：按钮不能只是摆设；创建、提交、审核、退回、评分、归档、导出等操作必须能在演示中产生可见结果。
6.  **不伪装真实能力**：页面应在合适位置说明当前为本地演示数据，不提供真实登录、服务端文件存储或跨设备同步。
7.  **先做最小可用，不做功能堆叠**：不开发
    AI、游戏化、排行榜、复杂报表和大型即时通讯功能。

## 2. 本版本范围

### 2.1 必须实现

-   演示登录与角色切换：学生、教师、管理员。
-   首页工作台：根据当前角色展示待办、项目状态和最近动态。
-   教师发布课程项目任务，设置组队规则、截止时间、阶段/里程碑和阶段成果要求。
-   教师决定该任务是否允许跨班组队。
-   学生查看可参与任务，由项目负责人创建项目并在创建时选择成员。
-   项目申请提交、教师审核、退回修改、审核通过。
-   项目空间：项目概览、成员、任务看板、里程碑、资料、讨论、阶段成果、最终成果。
-   教师发布或调整阶段要求，查看相关项目提交的阶段成果并进行评价。
-   项目讨论流：文字消息、@成员、代码片段/代码交流展示、附件引用或附件入口。
-   资料上传、下载、分类、常用文件预览和源码语法高亮。
-   队长提交结项；登记团队成果、每位成员的职责与个人贡献；队长提出贡献比例。
-   教师审核贡献比例、录入个人最终成绩与评语；可选录入外部专家评分，外部专家不需要系统账号。
-   结项审核通过后自动归档；教师可以将归档项目移出归档后再修改。
-   站内通知：任务发布、项目审核结果、阶段要求/截止提醒、成果退回、@提及、评分结果等。
-   学生个人项目档案：按学年/时间展示项目经历，支持补录历史项目记录。
-   导出学生个人项目履历 PDF。
-   单独导出项目介绍 PDF。
-   项目公开分享页：支持预览、复制链接、二维码展示或生成；公开页只展示允许公开的项目简介与已审核成果。
-   管理员导入演示账号及基础数据：提供 Excel
    模板下载、文件选择、导入预览、基础校验和导入结果反馈。
-   搜索与筛选：项目名称、任务名称、成员、文件名等基础字段。
-   浏览器本地持久化、恢复默认演示数据功能。

### 2.2 明确不做

-   不开发后端、数据库服务、服务端 API 或真实账号认证。
-   不接入学校统一身份认证、教务系统或真实 Excel 数据服务。
-   不做 AI 问答、AI 生成内容、智能评分等 AI 功能。
-   不做积分、勋章、排行榜、点赞排名、推荐算法等游戏化功能。
-   不做私聊、语音/视频会议、多频道即时通讯、WebSocket 实时协作。
-   不做 Git 仓库深度集成、在线 IDE、多人协同编辑或代码审查。
-   不做外部专家账号体系；专家评分由教师代为录入。
-   不做独立移动 App；桌面端优先，关键页面兼容常见手机宽度。
-   不做复杂组织架构、可配置审批工作流或大规模数据分析。
-   不将聊天记录、内部讨论、草稿和中间产物暴露到公开分享页。
-   不在学生端提供修改项目整体基本信息、删除项目或自行修改正式成员名单的能力。

## 3. 用户角色与权限

### 3.1 学生

学生可以：

-   查看自己所在教学班可参与的教师课程任务。
-   在创建项目时担任项目负责人，并选择团队成员。
-   查看自己参与的项目和项目详情。
-   在项目空间查看任务、阶段要求、成员、资料、讨论和成果。
-   完成分配给自己的任务；更新自己负责任务的状态。
-   上传项目资料、查看/下载资料、发布讨论消息、@项目成员。
-   提交阶段成果所需材料；由项目负责人提交项目结项。
-   填写自己的项目职责、个人贡献说明和佐证材料。
-   查看队长提出的贡献比例；项目负责人可提交团队成员贡献比例建议。
-   查看教师审核意见、阶段评价、个人最终成绩。
-   查看和补录个人历史项目档案。
-   导出个人项目履历 PDF。
-   对已允许分享的项目查看分享设置、预览分享页并复制链接/查看二维码；不得自行决定学号等个人字段的公开方式。

学生不可以：

-   创建教师尚未发布的正式课程项目任务。
-   在项目申请提交后自行更换正式成员；教师可在必要时调整。
-   修改已审核项目的整体基本信息。
-   删除项目。
-   归档项目或自行修改教师评分。
-   以队长身份给其他成员擅自创建或指派任务。学生可创建分配给自己的个人任务；需要分配给其他成员的正式任务由教师发布。
-   修改学号的公开规则或自行选择公开个人学号。

### 3.2 教师

教师可以：

-   查看与自己授课、发布任务或审核关系相关的项目。
-   查看自己关联的课程、教学班及学生名单演示数据。
-   创建、编辑、发布和关闭课程项目任务。
-   设置任务说明、组队人数、组队截止时间、是否允许跨班组队、项目申请截止时间。
-   为任务设置阶段/里程碑、阶段截止时间、提交要求和验收标准。
-   发布阶段性要求，查看项目团队的阶段成果提交。
-   审核项目申请：通过或退回，并填写原因；必要时修改项目基本信息或成员。
-   参与项目讨论、发布指导意见、查看项目资料和协作记录。
-   查看、评价阶段成果和过程表现。
-   审核最终成果、查看队长提出的贡献比例、调整/确认贡献情况。
-   录入项目总评、个人最终成绩、评语、评分人和评分时间。
-   可选录入外部专家姓名/单位、评分和意见；该评分可纳入正式项目评价，是否存在专家评分不是必填条件。
-   通过结项审核后将项目自动归档；将归档项目移出归档后再修改。
-   编辑项目整体基本信息；处理成员变更等特殊情况。
-   管理关联项目的分享状态与公开成果内容。

### 3.3 管理员

管理员可以：

-   查看系统演示概况。
-   查看、搜索学生与教师账号演示数据。
-   下载 Excel 导入模板。
-   导入或更新账号、课程、教学班、行政班和选课关系等基础数据。
-   预览待导入内容、查看错误行与校验结果、确认导入。
-   查看项目列表及项目状态，处理演示环境中的异常数据。
-   恢复默认演示数据。

管理员不需要在本版本中配置复杂权限规则，也不需要开发复杂的院系组织架构管理。

## 4. 核心业务流程

### 4.1 教师发布课程项目任务

1.  教师进入"课程任务"。
2.  点击"新建任务"，填写任务名称、所属课程、教学班、任务说明、组队人数范围、组队截止时间和项目申请截止时间。
3.  设置"允许跨班组队"开关。
    -   关闭：学生只能从当前任务允许的教学班学生名单中选择队友。
    -   开启：可以从演示数据中选择其他教学班学生。
4.  添加一个或多个阶段/里程碑。每个阶段包含名称、说明、截止时间、需要提交的材料和验收标准。
5.  发布任务。发布后，该任务出现在符合条件学生的"可参与任务"列表中，并产生站内通知。
6.  教师可以编辑尚未关闭的任务；任务关闭后，学生不能再基于该任务创建新项目，但已有项目仍可继续完成。

### 4.2 学生创建团队项目

1.  学生从"可参与任务"进入任务详情。
2.  点击"创建项目"，填写项目名称、项目简介、项目目标、技术/主题标签（普通文本即可）等基本信息。
3.  创建者自动成为项目负责人。
4.  负责人在创建页面选择成员并确认团队名单。若任务不允许跨班组队，成员选择器必须过滤掉不符合条件的学生。
5.  项目成员在提交时自动加入团队，不需要额外接受邀请。
6.  提交后项目状态变为"待审核"，成员名单锁定；学生不能自行更换成员。教师退回申请时，负责人可修改申请文字信息后重新提交，但成员调整仍由教师处理。
7.  同一学生在同一个课程任务中，演示规则下最多加入一个团队项目，避免重复组队。

### 4.3 教师审核项目申请

1.  教师在"项目审核"查看待审核项目。
2.  进入详情，检查项目简介、任务匹配情况、团队成员和组队规则。
3.  教师可选择：
    -   **审核通过**：项目状态变为"进行中"，项目基本信息和成员名单对学生锁定。
    -   **退回修改**：填写退回原因，项目状态变为"待修改"；负责人修改申请信息后重新提交。
4.  审核操作记录审核人、时间、决定和意见，并通知项目成员。
5.  审核通过后，项目工作区的任务、资料、讨论、阶段成果等功能开放。

### 4.4 项目过程协作

项目工作区包含以下核心区域：

-   **项目概览**：项目基本信息、状态、负责人、成员、当前阶段、进度摘要、最近动态。
-   **任务看板**：按"待开始 / 进行中 / 待验收 /
    已完成"等状态展示任务；支持创建分配给自己的任务、修改自己负责任务的状态、查看截止日期。教师发布的任务和阶段要求必须与普通个人任务明显区分。
-   **里程碑/阶段**：展示教师发布的阶段名称、截止时间、提交要求、验收状态和教师意见。
-   **资料库**：上传、分类、预览、下载文件；显示文件名、类别、上传者、上传时间和大小。
-   **讨论区**：项目内文字讨论、@成员、代码片段展示和附件引用。教师可以参与关联项目的讨论。
-   **成果区**：提交阶段成果、查看退回意见、提交最终成果、登记团队成果和成员个人贡献。
-   **成员区**：查看成员、项目角色、职责说明和贡献记录。
-   **动态记录**：展示项目关键操作，如任务发布、资料上传、阶段提交、审核、评分和归档。

讨论区不做私聊，不要求实时推送。演示中发送消息后应立即更新当前页面，并保存到本地状态。

### 4.5 阶段成果提交与验收

1.  教师在课程任务中预先设置阶段/里程碑，也可以在项目进行中补充阶段要求。
2.  所有该任务下的项目都能看到适用的阶段要求。
3.  项目成员可以准备材料，但由项目负责人或教师指定的提交人提交阶段成果。
4.  阶段提交至少包含提交说明和所需文件；具体字段根据教师设置的要求显示。
5.  提交后状态为"待验收"，教师可查看内容、填写分数和评语，并选择"通过"或"退回修改"。
6.  退回后展示教师意见，项目团队可以重新提交；历史提交记录在演示中保留。
7.  每次提交、退回、通过都产生动态记录和相关通知。

### 4.6 结项与个人贡献

1.  项目达到结项条件后，由项目负责人点击"提交结项"。
2.  结项表单至少包含：
    -   项目总结/项目介绍；
    -   最终成果说明；
    -   最终成果文件，必须包含源文件或代码材料；
    -   成果截图/图片；
    -   可选的外部作品链接，例如 B 站视频或公开仓库链接；
    -   每位成员的角色、职责、个人贡献说明及佐证材料。
3.  团队成果统一记录一次，不为每个成员重复创建一份团队成果。
4.  项目负责人为每位成员提出贡献比例建议，所有成员比例合计必须为
    100%。前端应即时显示总和，并在不等于 100% 时阻止提交。
5.  教师审核结项材料与贡献建议，可以确认或调整贡献情况，并分别录入个人最终成绩和评语。
6.  贡献比例作为教师确定个人成绩的重要依据；本版本不擅自设定"项目总分乘贡献比例"等自动计算公式，最终个人成绩由教师明确录入。
7.  教师可选录入外部专家评分和意见。外部专家不登录系统；教师代为录入。存在外部评分时，可在最终评价中作为正式评分的一部分。
8.  教师通过结项审核后，项目自动进入"已归档"，并保留全部项目资料、提交记录、评分和成员贡献。
9.  结项被退回时，项目进入"结项待修改"，负责人补充材料后再次提交。
10. 已归档项目默认只读；只有教师执行"移出归档/重新开放"后才允许继续修改。重新开放和再次归档都要有操作记录。

### 4.7 个人项目档案与导出

-   个人档案按学年/时间顺序展示参与过的项目。
-   每条项目经历展示项目名称、时间、课程/教学班（允许公开班级）、个人角色、个人职责、个人贡献、教师确认的成绩和成果摘要。
-   支持按学年、项目状态和关键词筛选。
-   允许学生补录历史项目记录。补录内容必须明确标注为"历史补录"，不伪装成当前系统中经过教师审核的项目；可以在档案中编辑和删除尚未认证的补录记录。
-   "导出个人项目履历"生成独立
    PDF，内容为该学生的项目经历与个人贡献，不包含聊天记录、内部资料或其他成员的私人信息。
-   导出的 PDF
    使用清晰的标题、基本个人信息、项目经历时间线、职责/贡献和成果摘要；页面需适合打印。
-   学号在个人档案公开页和项目导出内容中默认不展示。学生不能通过开关改变学号的公开规则。

### 4.8 项目介绍导出与公开分享

项目介绍导出与个人项目履历是两个独立入口、两种不同的输出内容。

**项目介绍 PDF 应包含：**

-   项目名称、项目简介、目标和背景；
-   关联课程/教学班（班级允许公开）；
-   项目时间、项目状态；
-   项目成员姓名与角色（不展示学号）；
-   已审核的最终成果说明、成果截图和视频链接；
-   教师评价或已确认的项目成绩（按权限决定是否展示）。

**公开分享页规则：**

-   通过链接或二维码访问，无需登录。
-   页面围绕项目简介、团队介绍、成果截图/视频和已审核的最终成果。
-   不公开学号；班级可以展示。
-   不展示项目聊天记录、内部讨论、任务评论、草稿、未审核材料、内部中间产物和仅供项目成员访问的文件。
-   不提供"公开学号"之类的学生个人设置。隐私规则由系统统一控制。
-   项目负责人可以查看分享预览并在权限允许时启用/关闭分享；教师可以管理分享状态。
-   关闭分享后，演示路由应显示"该项目暂未公开"页面，而不是继续暴露项目内容。
-   分享页与登录后的项目工作区使用不同布局和数据选择逻辑，不得直接把内部项目详情页原样公开。

### 4.9 站内通知

本版本实现普通站内通知，不做邮件、短信或系统推送。

通知类型至少包括：

-   教师发布新课程任务；
-   项目申请通过或退回；
-   教师发布/调整阶段要求；
-   阶段截止日期提醒（演示中可根据静态日期生成提醒，不要求后台定时任务）；
-   阶段成果通过或退回；
-   有成员在讨论中 @ 当前用户；
-   项目结项审核通过或退回；
-   教师录入或更新评分。

通知支持已读/未读、全部标记已读、点击跳转对应任务/项目/提交记录。用户操作后通知状态必须更新并持久化。

### 4.10 管理员 Excel 导入演示

管理员页面提供基础数据导入能力，至少包括：

-   学生/教师账号；
-   课程；
-   行政班；
-   教学班；
-   学生与教学班选课关系。

每种数据提供 Excel
模板下载，模板字段要有清晰的中文列名和示例行。导入流程为：选择文件 →
读取并预览 → 基础校验 → 展示成功/失败行 → 用户确认导入 →
更新前端演示数据。

本版本无需实现真实教务数据同步或复杂的数据合并策略，但不能只做一个无功能的"上传"按钮。导入后，新增数据应能在相应的账号、任务和成员选择器中被看到。对于无法解析的文件、缺少必填列或重复关键标识，应展示可理解的错误信息。

## 6. 关键页面的交互要求

### 6.1 演示登录与角色切换

-   登录页提供三个清晰的演示入口：学生、教师、管理员。
-   每个入口可使用预置演示账号直接进入，不请求真实服务器。
-   登录后顶部显示当前身份和姓名。
-   为便于演示，可以在用户菜单中提供"切换演示身份"；切换后路由、菜单和权限立即变化。
-   不把演示登录描述为安全的真实身份认证。

### 6.2 工作台

-   根据当前角色显示不同的摘要卡片和待办列表。
-   摘要卡片可点击并跳转到对应列表。
-   展示最近项目动态和通知摘要。
-   所有数量必须来自当前本地状态计算，不使用每次刷新都变化的随机数。

### 6.3 列表与搜索

-   列表提供关键词搜索、状态筛选和必要的排序。
-   搜索至少覆盖当前页面可见的名称字段。
-   无结果时展示空状态和清除筛选入口。
-   列表项点击后进入详情。
-   新建、编辑、审核等操作完成后，列表与统计数字立即更新。

### 6.4 表单

-   必填字段明确标识。
-   提交前进行基础校验，错误信息贴近对应字段。
-   保存成功后显示清晰反馈并更新页面。
-   取消操作应返回上一页或关闭弹窗，不得误提交。
-   破坏性操作需要二次确认；学生端不提供删除项目入口。

### 6.5 任务看板

-   支持按状态分栏展示任务。
-   任务卡显示标题、负责人、截止日期、状态和来源（教师阶段要求/个人任务）。
-   学生只能创建分配给自己的普通任务，不能将任务指派给其他成员。
-   教师发布的阶段要求由教师维护，学生不能修改其要求、截止时间或验收状态。
-   更新任务状态后，任务卡应立即移动到对应分栏并保留本地状态。

### 6.6 讨论区

-   消息显示头像或姓名缩写、发送者、时间、正文。
-   支持文本消息与 @成员。选择
    @成员后，消息正文中保留可识别的提及标记，并给被提及用户生成站内通知。
-   支持代码块输入/展示，代码块应保留缩进并使用语法高亮。
-   支持引用资料库中已有的文件记录，避免同一资料仅为在消息中出现而重复创建文件记录。
-   当前用户发送后立即显示；刷新页面后仍能看到历史消息。
-   不实现私聊、在线状态、已读回执或复杂富文本编辑器。

### 6.7 文件上传、预览与下载

-   文件按项目归属，并可选择简单分类，例如：文档、图片、代码、压缩包、其他。
-   显示文件名、类别、大小、上传者和上传时间。
-   图片和 PDF
    支持浏览器内预览；纯文本和常见源码支持只读预览与语法高亮。
-   对不能直接预览的格式提供下载入口和文件信息。
-   上传新文件时，默认作为新文件记录；如果产品界面提供"替换文件"，替换后应覆盖旧文件内容并保留必要的更新者/更新时间信息，不需要完整版本控制。
-   上传后可以下载回本地；文件信息和内容在当前浏览器演示环境中尽可能持久保存。
-   文件大小限制应在界面上明确提示，并对不支持的类型给出友好错误。
-   公开分享页不得读取或显示项目内部资料库中的全部文件，只能读取已明确标记为公开的最终成果材料。

### 6.8 PDF 导出

-   "导出个人项目履历"和"导出项目介绍"是两个独立按钮、两个独立模板。
-   导出前允许预览将被导出的内容。
-   导出文件名包含清晰的主体名称，例如"个人项目履历_姓名.pdf""项目介绍_项目名称.pdf"。
-   中文字体、分页、长文本换行和图片尺寸必须基本正常。
-   如果浏览器环境不支持直接生成
    PDF，可提供打印专用页面并调用打印功能作为明确的降级方式；不能让按钮无响应。
-   导出内容必须遵守隐私规则，不含学号、聊天记录、内部文件和未经审核的成果。

## 7. 项目状态与业务规则

### 7.1 项目状态

建议项目状态：

-   `待审核`：负责人已提交申请，等待教师审核。
-   `待修改`：教师退回项目申请，负责人可以修改申请文字信息后重提。
-   `进行中`：教师审核通过，项目协作功能开放。
-   `结项待审核`：负责人已提交最终成果，等待教师验收和评分。
-   `结项待修改`：教师退回结项材料，等待团队补充。
-   `已归档`：教师审核结项通过，项目默认只读。
-   `已关闭`：任务或教师管理导致项目停止继续开展；仅教师可处理。

"移出归档/重新开放"属于教师操作，不新增复杂的学生状态。重新开放后项目进入"进行中"，再次结项审核通过后重新归档。

### 7.2 阶段成果状态

-   未开始
-   进行中
-   待验收
-   退回修改
-   已通过

每次状态变化记录操作者、时间、意见和关联提交。

### 7.3 任务状态

-   草稿
-   已发布
-   已关闭

已发布任务可以被学生查看并创建项目；关闭后不再接受新的项目申请。

### 7.4 关键约束

1.  课程项目必须关联教师发布的课程任务和具体教学班。
2.  创建项目的负责人必须是当前登录学生。
3.  项目成员在创建时确定；提交申请后学生端不能自行更改名单。
4.  任务允许跨班组队时才允许选择其他教学班的学生。
5.  学生不能编辑已审核项目的整体基本信息，也不能删除项目。
6.  教师可修改项目基本信息、处理成员变更和移出归档。
7.  结项审核通过后自动归档。
8.  归档项目默认只读。
9.  队长提交的贡献比例总和必须为 100%。
10. 教师拥有个人最终成绩的确认权；贡献比例是评价依据之一，不自动替代教师评分。
11. 最终成果必须包含源文件/代码材料；图片、视频和外部链接可作为辅助证明。
12. 学号不在公开页面展示；班级可以展示；学生不拥有修改此规则的开关。
13. 公开页只展示明确允许公开的项目简介、成员公开信息和已审核最终成果。
14. 项目聊天记录、内部文件、草稿和中间产物始终不进入公开分享页。
15. 管理员导入后的数据要影响学生成员选择器、教师课程任务和相关列表。

## 8. 前端模拟数据与持久化要求

### 8.1 数据实现方式

-   只使用前端模拟数据，不建立后端服务或真实 API。
-   首次启动时加载固定、可重复的种子数据。
-   业务操作通过统一的本地数据层完成，不要在每个页面里各自维护互不相干的假数组。
-   建议使用 Pinia 管理会话、项目、任务、成员、通知、资料和评价状态。
-   轻量文本和业务记录可存入 `localStorage`；上传文件二进制优先存入
    `IndexedDB`，避免把大文件直接塞进 `localStorage`。
-   页面刷新后应恢复已创建的项目、消息、任务状态、通知已读状态、评分和导入的数据。
-   提供"恢复默认演示数据"功能，清除当前演示修改并重新加载种子数据。
-   如文件存储失败，应显示明确提示，不可静默假装上传成功。

### 8.2 演示数据最低要求

至少预置：

-   1 个管理员账号；
-   2 个教师账号；
-   8--12 个学生账号，分布在至少 2 个行政班/教学班；
-   2--3 门课程；
-   2 个教学任务，其中至少一个允许跨班组队、一个不允许；
-   3--5 个项目，分别覆盖待审核、进行中、结项待审核、已归档等状态；
-   每个示例项目有负责人、成员、任务、阶段、讨论消息、资料和动态记录；
-   至少 1 个阶段成果被退回，至少 1 个阶段成果已通过；
-   至少 1 个项目有完整的结项成果、贡献比例和个人成绩；
-   通知数据覆盖审核、@提及、阶段要求和评分等类型。

演示数据应稳定、内容合理、便于从不同角色走通主流程。不得使用随机数在每次刷新时改变核心数据。

### 8.3 数据关系建议

至少建立以下逻辑实体：

-   `User`：用户 ID、姓名、角色、学号（仅内部使用）、行政班、状态。
-   `Course`：课程 ID、课程名称、课程编号。
-   `TeachingClass`：教学班 ID、课程 ID、教学班名称、教师 ID 集合。
-   `Enrollment`：学生 ID、教学班 ID。
-   `CourseTask`：任务 ID、教师 ID、课程 ID、教学班
    ID、说明、组队规则、状态、截止时间。
-   `Milestone`：阶段 ID、任务 ID、名称、说明、截止时间、验收要求。
-   `Project`：项目 ID、任务 ID、名称、简介、负责人 ID、成员 ID
    集合、状态、创建时间、分享状态。
-   `ProjectTask`：任务 ID、项目 ID、标题、负责人
    ID、状态、截止时间、来源类型。
-   `ProjectSubmission`：提交 ID、项目 ID、阶段/结项类型、提交人
    ID、说明、文件 ID 集合、状态、提交时间。
-   `ProjectFile`：文件 ID、项目 ID、名称、分类、大小、上传者
    ID、上传时间、存储引用、是否公开成果。
-   `DiscussionMessage`：消息 ID、项目 ID、发送者 ID、正文、提及用户 ID
    集合、附件引用、时间。
-   `Contribution`：项目 ID、学生
    ID、职责、贡献说明、建议比例、教师确认比例（可选）、佐证材料。
-   `Evaluation`：评价 ID、项目/提交 ID、评价阶段、评分人
    ID、分数、评语、时间。
-   `Notification`：通知 ID、接收者
    ID、类型、标题、正文、关联路由、已读状态、时间。
-   `PortfolioRecord`：记录 ID、学生 ID、项目
    ID（历史补录可为空）、学年、角色、职责、贡献、成果摘要、是否历史补录。

字段可按实际代码简化，但必须保证项目、成员、任务、提交、评价和通知之间的关系一致。

## 9. UI 与视觉规范（强制执行）

本节是全项目所有页面的统一视觉约束，优先级高于页面局部的临时设计想法。学生端、教师端、管理员端必须使用同一套蓝色亮色 2D 管理系统设计，不得按角色切换成不同主题色。

### 9.1 设计目标

- 采用简洁、紧凑、清晰的传统 Web 管理系统风格，强调信息组织和操作效率。
- 全站以白色为主，蓝色用于主要操作、当前导航、链接和必要的状态强调。
- 使用平面化 2D 设计，不使用渐变、玻璃拟态、拟物效果、装饰性插画、光影、卡片投影或非必要动效。
- 页面不添加装饰性大色块背景。允许极少量浅灰色用于分隔线、表格隔行、禁用态和必要的选中态；不得用大面积彩色背景区分模块。
- 所有页面使用同一套字号、颜色、圆角、间距、边框、控件高度和图标规范。
- 不添加没有业务意义的欢迎标语、宣传口号、空泛描述、重复副标题或大号装饰标题。
- 标题只用于标明真实的页面名称、内容区名称或操作名称。例如“我的项目”“课程任务”“项目审核”，禁止“开启高效协作之旅”等宣传式文案。
- 不使用 emoji 作为界面图标。可使用统一的 SVG 矢量图标或同一套图标库。
- 任何页面都不应为了“视觉丰富”而增加无意义的图表、统计卡片、装饰线条、浮动按钮或动画。

### 9.2 全局设计令牌

1. 主内容区始终以白色为主，不使用渐变或有色大背景。
2. 主要按钮可使用主蓝色实心样式；次要按钮使用白色背景、浅灰边框和深色文字；危险操作使用明确的危险色文字/边框。
3. 不使用投影营造层级。通过间距、边框、字号和对齐关系建立层级。
4. 不允许同一类组件在不同页面出现不同圆角、不同高度或不同字体大小。
5. 颜色仅承担信息和交互含义，不用于无意义装饰。

### 9.3 布局与对齐

#### 整体框架

- 所有登录后的工作台统一使用“左侧导航 + 顶部栏 + 主内容区”的基础框架。
- 三种角色的导航结构可以不同，但布局尺寸、字体、图标、选中态、间距和交互方式必须一致。
- 顶部栏保持简洁，只保留必要的页面辅助入口、通知和当前用户菜单，不放置大幅品牌标语或装饰性欢迎语。
- 主内容区从统一的左上起点开始。页面标题、筛选区、主要操作区、表格/内容区之间遵循统一间距。
- 不使用多层嵌套卡片。能直接用标题、分隔线和内容区表达的地方，不再额外套卡片。
- 卡片仅用于确实需要分组的内容；默认白底、细边框、无阴影。

#### 侧边栏

- 所有端的侧边栏使用同一套宽度、内边距、图标尺寸、文字字号、行高和选中态。
- 导航项高度建议 `40px`，点击区域必须覆盖整行，而不是只有图标或文字可点击。
- 导航项左右内边距统一为 `12px`；图标与文字间距统一为 `8px`。
- 图标与文字垂直居中；所有导航项的图标左边缘和文字左边缘分别对齐。
- 导航项上下间距统一，建议相邻项之间 `4px`；分组之间可以使用 `12px` 的间距。
- 侧边栏文字不得因留白过大而被不必要地截断。常用菜单应在默认宽度下完整显示。
- 当前页面使用浅蓝底色或左侧细蓝色指示条表达选中状态，不使用渐变、发光或跳动效果。
- 导航分组标题如非必要则不显示；必须显示时使用 `12px` 次级文字，避免额外留白。
- 折叠状态下图标居中，点击区域尺寸不变，并提供可访问的文字提示。

#### 页面标题与操作区

- 页面标题统一为 `20px`、中等字重，紧邻标题的说明只在有实际帮助时出现。
- 页面标题、面包屑、操作按钮不得重复表达相同内容。
- 主要操作放在页面标题行右侧或列表工具栏中，位置保持一致。
- 搜索框、筛选器和操作按钮在同一工具栏内按统一间距排列；窄屏时自然换行，不得相互覆盖。
- 不要在每张卡片上重复放置“详情”“查看”等冗余标题；直接使用明确的操作按钮或链接。

### 9.4 字体、行高与文字内容

- 全站统一使用系统中文无衬线字体栈，例如 `Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", sans-serif`。
- 基础文字统一为 `14px`。辅助说明使用 `12px`，页面标题使用 `20px`，区块标题使用 `16px`。除特殊数据展示外，不得随意创建 `13px`、`15px`、`18px` 等额外字号层级。
- 表格、表单、菜单、按钮、弹窗和详情页中的同类文字必须保持字号一致。
- 正文行高建议 `1.5`；表格单行内容垂直居中；表单标签与输入控件保持固定对齐关系。
- 文字与图标之间统一使用 `8px` 间距；多个图标之间统一使用 `8px` 间距。
- 每行文字必须能在合理宽度内完整阅读。对长标题、文件名和项目名称采用合理换行或省略号，并提供完整文本查看方式；不能让文字与图标、按钮重叠。
- 表格列宽应优先满足关键信息可读。操作列应预留足够宽度，不允许多个按钮挤压成难以点击的小图标。
- 表单错误提示应紧贴对应字段，使用统一字号与错误色；提示文字不得挤压或覆盖输入框。

### 9.5 圆角、间距与点击区域

- 全站统一采用 `4px` 小圆角和 `6px` 通用圆角。按钮、输入框、下拉框、弹窗、标签和容器不得各自使用不同圆角体系。
- 禁止大圆角胶囊按钮、超圆角卡片和无必要的圆形装饰；仅允许小型状态标签根据组件库规范使用轻微圆角。
- 页面主内容的水平间距、标题与内容区间距、表单项间距、表格工具栏间距都必须来自全局间距令牌。
- 同一行的输入框、下拉框和按钮必须高度一致并垂直对齐。
- 普通按钮和输入控件的高度不得低于 `36px`；主要操作点击高度建议 `40px`。
- 导航项点击高度不低于 `40px`；表格行内操作应提供足够的点击区域，不得只让 16px 图标本身可点击。
- 可点击的图标按钮建议至少有 `32px × 32px` 的操作区域；重要的表格操作优先使用文字按钮或下拉操作菜单。
- 点击区域之间要留出间距，避免误触；删除、归档、关闭分享等影响较大的操作需要二次确认。
- 弹窗宽度、内边距、按钮区和标题区使用统一规则。弹窗不得超出视口，也不能因留白过大而显得松散。

### 9.6 图标规范

- 使用统一的 SVG 矢量图标库，例如 `lucide-vue-next`，不混用来源、线宽和视觉风格差异明显的图标。
- 图标默认 `16px`，少量主要入口可使用 `20px`。
- 图标默认采用深灰色；当前导航、主要操作和链接可使用主蓝色；成功、警告和错误图标仅使用对应状态色。
- 同一类操作在所有页面必须使用同一图标。例如新增、编辑、删除、下载、上传、搜索、筛选、通知、返回等操作不得换用不同图形。
- 线条粗细、端点、尺寸和视觉重量应保持一致。
- 图标必须表达明确含义；无法明确表达时使用带文字的按钮，不得仅依赖图标猜测操作。
- 图标与文字的间距统一；带图标按钮中图标位置保持一致。
- 不使用 emoji、彩色拟物图标、3D 图标或带光效图标。

### 9.7 表格、表单、弹窗与状态组件

#### 表格

- 采用白底、细边框和清晰的列分隔；不使用厚重阴影或大面积彩色表头。
- 表头字号 `12px` 或 `14px`，全站统一选定一种，不得在不同页面随意变化。
- 常规行高 `44px` 至 `48px`，内容垂直居中。
- 表格工具栏统一放置搜索、筛选和主要操作；不把主要操作散落在表格上下多个位置。
- 操作列中的按钮保持统一顺序、尺寸和间距。
- 空列表必须显示简洁的空状态与必要操作，不显示宣传式插画或空泛文案。

#### 表单

- 标签字号统一为 `14px`，输入内容为 `14px`，辅助提示为 `12px`。
- 同一表单内输入控件高度、圆角、边框颜色和间距一致。
- 表单按业务逻辑分组；只有字段较多且确有必要时才使用分组标题。
- 必填项、校验失败、禁用和只读状态使用统一样式。
- 保存、取消按钮的顺序和位置全站统一。

#### 弹窗与抽屉

- 只用于确认、编辑或查看确实需要浮层呈现的内容。
- 不使用背景模糊、玻璃拟态、阴影光晕或夸张进出场动画。
- 弹窗标题、正文、表单区、底部按钮区使用统一间距。
- 重要操作明确说明将发生的结果；取消始终可用。

#### 状态与反馈

- 项目、任务、成果和审核状态使用统一的状态标签组件。
- 状态色只用于文字、边框或小面积浅色提示，不为整行或整张卡片铺设大面积彩色背景。
- 成功、失败、校验错误和权限不足都要有可理解的反馈。
- 反馈提示样式统一，不使用夸张动画或长时间遮挡内容的弹窗。

### 9.8 页面密度与响应式

- 桌面端优先，保证 `1366×768` 分辨率下主要工作流无需横向滚动。
- 主内容区应紧凑，但不能压缩到文字拥挤或点击困难。
- 减少大面积空白和重复卡片；列表、表格和表单应优先利用可用宽度。
- 常用操作应尽量在首屏可见；次要信息可通过详情页、折叠区或弹窗查看。
- 当屏幕宽度不足时，工具栏可以换行，侧边栏可以折叠，表格可采用明确的横向滚动或移动端卡片布局；不得把桌面布局简单缩小到无法阅读。
- 响应式适配不得引入另一套字号、圆角和颜色体系。

### 9.9 GitHub 开源项目参考要求

Codex 在设计任何页面或功能之前，必须优先研究成熟开源项目的现有实现，不得凭空设计一套与常见管理系统交互不一致的界面。

首选参考仓库：

1. [SoybeanAdmin](https://github.com/soybeanjs/soybean-admin)：参考 Vue 3 管理系统的目录结构、页面布局、路由、权限导航、常见表单和列表组织方式。
2. [Vue Vben Admin](https://github.com/vbenjs/vue-vben-admin)：参考管理后台的整体框架、导航组织、可复用页面组件、权限路由和常见管理页面模式。
3. [vue-element-admin](https://github.com/PanJiaChen/vue-element-admin)：参考成熟管理系统的表格、筛选、表单、详情、批量操作和后台业务流程；该仓库属于较早的技术体系，只参考成熟交互模式，不照搬过时依赖。
4. [Element Plus](https://github.com/element-plus/element-plus)：如当前项目采用 Element Plus，优先使用其成熟的表格、表单、对话框、分页、下拉选择、消息反馈等组件及其标准交互，不重复造轮子。

执行要求：

- 开始页面开发前，先阅读上述仓库的 README、目录结构、页面示例和组件文档；根据当前工程技术栈选择适用的参考对象。
- 重点借鉴成熟的布局、导航、列表筛选、表格、表单、弹窗、状态标签、分页、空状态和反馈模式。
- 先建立本项目的统一 `AppShell`、侧边栏、顶部栏、页面标题、列表工具栏、表格、表单、弹窗和状态标签，再开发业务页面。
- 优先使用当前项目已有的 UI 组件库；如果已有组件库足以满足需求，不要再安装第二套大型 UI 库。
- 参考开源项目不等于直接复制整套项目。只借鉴与本需求有关的布局和交互模式，遵守其许可证；不要复制与本项目无关的模块、复杂主题系统或大规模基础设施。
- 如果可以访问 GitHub 页面或仓库源码，应以实际代码和文档为依据；不得仅凭项目名称猜测其设计。
- 如果某个仓库暂时无法访问，记录无法访问的情况，并改用其他可访问的成熟开源参考，不得声称已经阅读。
- 在实现报告中简要列出实际参考过的仓库、参考了哪些模式、哪些部分沿用了现有组件库。
- 参考过程中必须服从本需求书的统一视觉约束：不因参考项目存在多主题、渐变、阴影或复杂动效，就把这些效果引入本项目。

### 9.10 UI 验收标准

- [ ] 学生端、教师端、管理员端使用同一套蓝色亮色主题。
- [ ] 页面以白色为主，没有渐变、装饰性大色块、阴影、光晕或非必要动效。
- [ ] 全站字号遵循统一层级，没有随意增加的字号。
- [ ] 全站圆角、控件高度、图标尺寸和常用间距一致。
- [ ] 侧边栏宽度、导航项留白、图标与文字间距和选中态一致。
- [ ] 每行文字有足够空间，不与图标、按钮或其他文字重叠。
- [ ] 按钮、导航、表格操作的点击区域足够大，易于操作。
- [ ] 页面没有宣传口号、空泛标题或重复的无意义描述。
- [ ] 所有图标来自统一 SVG 图标体系，配色协调，语义明确。
- [ ] 表格、表单、弹窗、通知和状态标签遵循统一组件规范。
- [ ] 主要页面的设计和交互模式有明确的开源参考依据。
- [ ] 在 `1366×768` 桌面尺寸下，主要页面无明显溢出、重叠或不可读区域。
- [ ] UI 不只是静态外观；所有已展示的主要操作仍必须具备真实的前端交互。

## 10. 技术实现建议与 Codex 开发约束

### 10.1 技术建议

如果当前仓库已有技术栈，先检查并沿用，不要无理由重建工程。如果仓库为空，可采用：

-   Vue 3
-   Vite
-   TypeScript
-   Vue Router
-   Pinia
-   Element Plus 或同等成熟的 Vue UI 组件方案
-   统一 SVG 图标库，例如 `lucide-vue-next`
-   `xlsx`：浏览器端读取和生成 Excel 模板
-   `highlight.js` 或 `Prism.js`：源码/代码块高亮
-   PDF 生成库或打印专用页面：实现两类 PDF 导出
-   二维码库：生成分享二维码

不要安装与当前功能无关的大型依赖。不要为了本版本创建 Java
后端、数据库、服务端接口或部署配置。

### 10.2 Codex 必须遵守

1. **先研究开源项目再设计页面**：按照第 9.9 节查看 SoybeanAdmin、Vue Vben Admin、vue-element-admin 和当前工程使用的 UI 组件库；记录实际参考的布局、表格、表单、导航和交互模式。不得凭空从零设计所有组件。
2. **先统一设计系统再铺开页面**：先实现全局颜色、字号、间距、圆角、控件高度、图标尺寸、侧边栏和通用组件，再实现各业务页面。
3. **所有端统一蓝色亮色 2D 风格**：禁止按角色使用不同主色；禁止渐变、阴影、光效、玻璃拟态、装饰性背景色块和非必要动画。
4. **严格执行统一尺度**：页面、表格、表单、按钮、弹窗、图标和导航的字号、圆角、间距、尺寸必须来自统一令牌，不允许页面自行发明样式值。
5. **禁止无意义文案**：不得添加宣传口号、空泛欢迎语、无业务价值的标题和重复说明。页面标题只写真实的业务名称。
6. **复用成熟组件**：优先使用项目中已有 UI 组件库；避免重复造轮子或同时引入多套组件库。参考开源项目时遵守其许可证，只借鉴适用模式，不整套复制无关模块。
7. 开始前检查当前目录、现有文件、`package.json`、路由和已有组件；先理解现有工程，再决定新增或修改哪些文件。
8. 如果仓库已有可运行的 Vue 工程，优先在现有结构中完成，不要清空重建。
9. 不修改 `.env`、密钥、系统级配置或与当前原型无关的文件。
10. 不创建后端，不连接真实数据库，不调用真实业务 API。
11. 业务数据必须通过统一的 mock repository/store 管理，避免页面之间数据各自独立。
12. 所有主要按钮都必须完成对应的前端动作，不能只展示静态 UI。
13. 先实现完整主流程，再完善视觉细节；不要为了反复验证而陷入无止境的重构。
14. 不要擅自扩展 AI、游戏化、排行榜、私聊、Git 深度集成等明确排除的功能。
15. 不要擅自更改项目规则，例如让学生修改审核通过后的项目基本信息、让学生删除项目、让队长给其他成员创建任务或公开学号。
16. 代码结构清晰、命名一致、组件可复用；避免把全部页面写进单个巨大组件。
17. 为关键状态变化提供统一的数据操作方法，保证通知、动态记录、列表计数和详情页同步更新。
18. 交付前运行项目构建/类型检查；修复阻断运行的问题。若某条检查因环境缺失无法运行，应如实说明。
19. 最终报告应简要列出已实现页面、已跑通的业务流程、运行命令、已知限制和未实现事项，不要声称完成了真实后端或真实多人协作。

### 10.3 建议实现顺序

1.  工程检查、基础布局、路由、主题和演示身份切换。
2.  Mock 数据模型、统一 store、本地持久化和恢复默认数据。
3.  学生/教师/管理员工作台与导航。

7.  阶段成果提交、教师验收、结项提交、贡献比例和评分归档。
8.  通知中心、个人档案、历史项目补录。

11. 统一处理空状态、表单校验、权限控制、错误提示和响应式布局。

## 11. 最小验收清单

以下流程必须能在本地演示中完整跑通。不能只用静态页面模拟结果，关键状态必须实际变化。

### A. 任务发布与组队

-   [ ] 教师可以新建并发布课程任务。
-   [ ] 任务可以设置组队人数、截止时间和阶段要求。
-   [ ] "允许跨班组队"开关会实际影响学生成员选择范围。
-   [ ] 学生可以查看任务详情并创建项目。
-   [ ] 项目负责人可以在创建时选择成员。
-   [ ] 提交后项目状态变为待审核，成员名单对学生锁定。

### B. 审核与项目工作区

-   [ ] 教师可以通过或退回项目申请，并填写意见。
-   [ ] 审核结果会更新项目状态并产生通知。
-   [ ] 审核通过后项目工作区可以使用。
-   [ ] 学生无法修改审核通过后的项目基本信息，也无法删除项目。
-   [ ] 教师可以修改项目基本信息并处理成员变更。

### C. 过程协作

-   [ ] 项目任务看板可以展示和更新任务状态。
-   [ ] 学生不能把普通任务指派给其他学生。
-   [ ] 教师发布的阶段要求在项目中可见，学生不能改动要求本身。
-   [ ] 文件可以上传、分类、预览或下载；源码预览具有语法高亮。
-   [ ] 项目讨论消息可发送、刷新后保留。
-   [ ] @成员后，被提及用户收到站内通知。
-   [ ] 关键操作会进入项目动态记录。

### D. 阶段成果与结项

-   [ ] 项目负责人可以提交阶段成果。
-   [ ] 教师可以通过或退回阶段成果，记录分数/评语。
-   [ ] 项目负责人可以提交结项材料。
-   [ ] 结项表单要求最终成果源文件/代码材料。
-   [ ] 队长可以填写成员职责、贡献说明和贡献比例。
-   [ ] 贡献比例合计不等于 100% 时不能提交。
-   [ ] 教师可以确认贡献情况并录入个人最终成绩和评语。
-   [ ] 外部专家评分为可选项，且由教师录入。
-   [ ] 教师通过结项后项目自动归档。
-   [ ] 归档项目默认只读；教师移出归档后才能修改。

### E. 档案、导出与分享

-   [ ] 学生个人档案按时间展示项目记录。
-   [ ] 可以补录历史项目，并清楚标记历史补录。
-   [ ] 可以导出个人项目履历 PDF。
-   [ ] 可以独立导出项目介绍 PDF。
-   [ ] 分享页可通过链接访问，且与内部工作区分离。
-   [ ] 分享页不显示学号、聊天记录、内部资料、草稿或中间产物。
-   [ ] 关闭分享后，公开链接不再展示项目内容。
-   [ ] PDF 和分享页的中文、长文本和图片布局基本正常。

### F. 管理员与数据持久化

-   [ ] 管理员可以下载 Excel 模板并选择导入文件。
-   [ ] 导入前可以预览数据和错误行。
-   [ ] 确认导入后，新用户/课程/教学班能在相关页面中使用。
-   [ ] 页面刷新后项目、任务、消息、通知和评分等状态仍保留。
-   [ ] 恢复默认演示数据后，系统回到初始数据状态。
-   [ ] 三种角色的菜单和权限存在明显区别。
-   [ ] 项目能启动，主要路由可访问，没有明显控制台报错。

## 12. 最终交付要求

Codex 完成后，至少应交付：

1.  可运行的前端项目。
2.  清晰的项目启动说明（例如安装依赖与启动命令）。
3.  固定的演示账号及角色切换说明。
4.  已实现页面与核心流程清单。
5.  已知限制说明：无后端、数据保存在当前浏览器、无法跨设备/浏览器实时同步。
6.  验收清单执行结果；未通过的项目需明确列出，不得隐瞒。
7.  默认演示数据足够完整，首次启动后无需手工录入大量数据即可演示主流程。

**最终判断标准：**打开前端后，能够以教师身份发布任务，以学生身份组队创建项目，再以教师身份审核，以学生身份完成协作和结项提交，最后以教师身份完成评分归档，并能查看个人履历、导出
PDF、打开公开分享页。整个过程不依赖后端，也不应依赖外部真实账号。
